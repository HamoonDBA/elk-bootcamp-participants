Logstash · when to use it15 / 61

Use it when events need real work in transit

Good choice

  • Many formats to parse: grok, dissect, kv, json
  • Enrichment: geoip, lookups, user agent
  • Routing one stream to several outputs
  • Consuming Kafka into Elasticsearch at scale
  • Sources without a shipper: JDBC, HTTP, syslog

Think twice

  • On every host or container: too heavy
  • Simple JSON: an ingest pipeline is enough
  • Joins, windows, state: Flink or Kafka Streams
  • Exactly-once required: it is at-least-once
  • No one to operate another JVM service

Elasticsearch · why a cluster26 / 61

One node is a server; three nodes are a service

node-1healthy
node-2healthy
node-3down

The two survivors still hold a copy of every shard and still form a majority. Searches keep working.

Scale out

More data and traffic than one machine: add nodes, shards spread out.

High availability

Replicas on other nodes; a lost node’s shards are rebuilt elsewhere.

Parallel queries

Every shard searches its part at the same time.

Elasticsearch · document routing29 / 61

A hash picks the shard

shard = hash(_routing) % number_of_primary_shards_routing defaults to _id · murmur3 · simplified form

Default: by _id

Even spread. Every search asks every shard.

Custom routing

?routing=tenant_42 puts one tenant on one shard, so its searches touch one shard. A huge tenant makes a hot shard.

Consequence

Change the primary count and every hash moves. Hence fixed: use split, shrink or reindex.

Elasticsearch · how a query runs30 / 61

Scatter to every shard, gather, merge

Client

wants the top 10

Coordinating node

fans out, merges, returns

Shards, in parallelshard 0 · local top 10 + scoresshard 1 · local top 10 + scoresshard 2 · local top 10 + scores

1 · Query phase

Each shard finds its best ids and scores.

2 · Merge

The coordinator sorts 30 candidates, keeps the top 10.

3 · Fetch phase

Only those 10 documents are loaded and returned.

Aggregations: each shard computes a partial result and the coordinator reduces them. That is why terms counts and percentiles can be approximate.

Elasticsearch · shard size32 / 61

Too big hurts recovery; too many hurts the cluster

One 400 GB shard

  • Hours to copy when a node fails
  • Large merges eat I/O and space
  • One thread of search parallelism
  • Cannot spread to new nodes

Ten thousand 50 MB shards

  • Huge cluster state for the master
  • Per-shard memory and file overhead
  • A search fans out to thousands of tasks
  • Cause: daily indices for tiny sources
Aim for 10–50 GB and under 200 M docs per shardGET _cat/shards?v

Step 5 · the denominator54 / 61

A rate is only right if the denominator asks the same question

Wrong

No-result rate = results_count = 0 out of all requests. Failed requests also have 0 results, so outages look like empty searches.

Right

Out of successful requests with a valid count:

WHERE status == 200
  AND results_count IS NOT NULL
Step 5 · percentiles55 / 61

p95: the time that 95% of requests beat

Why not the average

A few 5-second timeouts pull the average up while most users saw 180 ms.

It is an estimate

TDigest. On our data ES|QL says 514 ms, Lens 531 ms. Compare trends, not digits.

Never average p95s

The mean of per-city p95 values is not the overall p95.

STATS p95_ms = PERCENTILE(response_ms, 95) BY city
